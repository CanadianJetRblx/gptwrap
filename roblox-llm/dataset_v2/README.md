# Roblox/Luau dataset v2

This is the follow-up dataset for Qwen3.5-4B. It is built from real GitHub Luau code, verified by
deterministic checks, and turned into two kinds of training examples. Nothing in it was written by
a model.

## What is in it

| Output (Volume `rbx-crawl`, `dataset_v2/out/`) | What it is |
|---|---|
| `cpt_train.jsonl.zst` | Verified files for continued pretraining, with provenance (repo, path, licence, stars, checks run, warnings, quality features) |
| `sft_train.jsonl.zst` | Instruction pairs: debugging tasks (`debug_detected_fault`) and header-comment-to-code tasks (`header_comment_to_code`) |
| `holdout_eval.jsonl.zst` | Verified files from repositories that never enter training |
| `eval/tasks.jsonl` | Held-out debugging tasks for scoring models (see `dataset_v2/eval_harness.py`) |
| `manifest.json` | Counts and every drop reason |

## Sources

Only GitHub code records from the crawl are used, because their repository and path are known.
Hugging Face datasets are excluded from v2 for two reasons: several are generated by language
models (for example a Gemini-named dataset and LLM-written reasoning sets), and for most of the rest
we cannot tell which file came from where. Documentation (Creator Hub, DevForum) is excluded from
v2 training for the same reason and stays available for retrieval.

Licences are recorded per file for provenance, but they do not gate inclusion. That is the policy
for this project.

## Verification

Each file must pass `dataset_v2/verify.py`. The checks, and what they can and cannot tell us:

- **structure:** Luau tokeniser; block keywords balance; brackets match; no open strings. Handles
  if-expressions, interpolated strings and type suffixes.
- **api (hard errors):** a `game:GetService("X")` name must be a real service in the engine API dump;
  `Instance.new("X")` must be a creatable class in the dump (deprecated classes are warnings).
- **boundary (hard errors):** a `.client` script must not reference server-only services.
- **soft warnings:** member names that are not in the dump and not defined in the same file (often
  defined in another module, such as Promise or Knit methods); deprecated APIs (`wait`, `spawn`,
  `BodyVelocity`, ...).

**What this is not:** static type checking, and not behavioural testing. A file that passes can
still have type errors or fail at runtime. The labels say which checks ran; nothing is labelled as
type-checked.

## Tasks

- **Debugging (`debug_detected_fault`):** take a clean file, apply one mutation (typo in a service
  or member name, dropped `end`, deprecated `task.wait` changed to `wait`, a server service inserted
  into a client script). The mutant is kept only if the verifier detects the fault. The response is
  the original file, which passed every check with no warnings.
- **Header comment (`header_comment_to_code`):** a file whose leading comment is substantive prose
  (licence text is removed) becomes an instruction, and the file is the response.

## Dedup and split

- Exact duplicates by normalised text (comments and whitespace removed).
- At most 150 training files per repository, so one project cannot dominate.
- Repositories are assigned to train or held-out by a stable hash (5% held out). Held-out
  repositories never reach training, and duplicates across the split are removed.

## Known limits

- Coverage is limited to what the verifier can check. Library-heavy code is down-weighted, because
  its member calls can't be resolved without its dependencies.
- Debugging tasks teach fixing faults the verifier can see. They do not teach subtle logic bugs,
  races or performance problems. Those need behavioural tests we don't have yet.
- The held-out benchmark is lint-level. It measures well-formedness, API correctness and fixing
  detectable faults. It does not measure whether a game works.
